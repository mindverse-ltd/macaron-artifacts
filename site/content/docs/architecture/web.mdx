The WebUI is a single Vite-built React application under `artifacts/src/web`. It does not select a different SPA for each harness: the active conversation tells the server which `HarnessAdapter` to use, while the browser keeps one consistent interaction model.

## Main surfaces

- `App.tsx` composes the sidebar, top bar, conversation, composer, Profile manager, and responsive Canvas split view.
- `src/web/chat` keeps a stable AI SDK Chat instance per session, queues messages for the owning session, and reconnects to active turns.
- `ArtifactPanel` discovers `.artifacts/canvases/*.ui4a.tsx`, shows source while it streams, and mounts the live Canvas when the module is ready.
- `src/web/components/profiles` edits harness-specific Profiles with Headless UI controls and applies changes from the next turn.
- `src/web/theme` maps Shiki workbench roles to semantic CSS variables shared by the host and generated UI.

## Rendering and accessibility

Host controls use native HTML plus Headless UI where behavior is stateful: dialogs, tabs, selects, disclosures, and menus retain keyboard navigation and focus management. UnoCSS `presetWind4` supplies the shared reset and utilities. Generated surfaces use a scoped Wind4 runtime so they cannot replace the host reset.

The layout preserves background turns when the selected conversation changes. Mobile viewports collapse Canvas into a drawer, and the split separator exposes its current value to assistive technology. Focus indicators come from the theme's focus token rather than from repeated container borders.

Streaming assistant prose uses Streamdown's 800 ms character fade with no stagger. New text enters the DOM immediately; the animation follows received text updates without buffering or replaying the response. User messages and restored history remain static, and reduced-motion preferences disable the visual fade.

Reasoning is visible by default. Summary updates show the latest entry while keeping earlier entries available; full reasoning uses a height-limited scrolling region with fading edges. Scrolling up pauses automatic following. The UI preserves independent AI SDK reasoning parts and their tool/text boundaries instead of joining them into one monologue. Streaming motion and automatic following stop when the turn ends or is interrupted.

The conversation follows growing content with an interruptible spring. Its target and growth velocity update from the current layout on each animation frame, so new lines do not restart the motion. The follow latch is independent of distance from the growing bottom: layout clamps, spring settling and programmatic focus cannot cancel it. Upward scrolling, text selection and deliberate control or keyboard navigation pause it; an explicit return or downward gesture reaching the tail resumes it. Native scrollbar dragging retains user control until release, and only releasing at the actual bottom resumes following. A streaming Canvas activates following and retains that latch through its final asynchronous layout, without rearming a reader's pause. Opening an existing static Canvas starts at the top. Reduced motion uses immediate following. Both hosts share these rules, and the viewport-bound root keeps scrolling inside the chat and Canvas panes rather than moving the document.

Adjacent tool calls share one collapsed status row, including progress and failures. Expanding it reveals every call in order with its arguments, output, and Canvas actions. Text, reasoning, images, and approvals separate groups; transport metadata and command output deltas do not create extra rows. Tool labels, reasoning, and assistant prose share a common text alignment, and toggling details preserves selectable output and keyboard focus.

Tool summaries include the actual files, search terms, and directories. Codex's native `commandActions` take precedence; structured tool arguments and a conservative shell parser cover other harnesses and older sessions. Repeated targets are deduplicated only in the summary. Unknown or mixed commands retain their generic description and full original input; activity labels are not permission classifications.

## Themes

The picker stores a paired light/dark family. Appearance (`auto`, light, or dark) remains independent from family selection, and only the variant matching the current appearance is loaded. Theme roles include editor, sidebar, title bar, menu, widget, input, dropdown, selection, focus, and optional borders; missing roles fall back to composited semantic values instead of painting every surface with a border.
